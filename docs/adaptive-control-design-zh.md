# LocalPilot 自适应推理控制方案

> 更新日期：2026-09-21
> 文档性质：产品与技术方案
> 状态说明：本文明确区分当前能力、比赛阶段计划和后续生产化能力。

## 1. 方案结论

LocalPilot 应从一次性的推理配置选择器，逐步发展为任务驱动的本地推理控制层：

> **根据业务目标、目标设备和运行状态，在合适的时机重新验证或调整模型配置，同时保护正在执行的任务。**

这项能力适合放进 LocalPilot，但职责必须拆开：

| 组成 | 职责 |
|---|---|
| LocalPilot Skill | 定义介入条件、诊断方法、验收规则、切换和回滚流程 |
| 监控器与规则引擎 | 持续采集指标，用确定性规则识别变化并触发流程 |
| 小型控制 LLM | 按需理解自然语言需求、归纳异常、解释方案和生成候选计划 |
| LocalPilot Core / CLI | 检测、规划、基准测试、验收、执行切换和保存证据 |
| 业务推理引擎 | 运行实际服务模型 |

小型控制 LLM 不应直接决定生产切换。最终动作必须经过确定性资源检查、真实验收和可回滚执行。

## 2. 当前能力边界

截至 2026-09-21，LocalPilot 已经能够：

1. 从自然语言解析任务、隐私、优先级、质量、上下文、并发、能力、模态和语言；
2. 检测本机或 SSH 目标节点的硬件指纹；
3. 将新需求与已保存 Profile 的结构化要求进行精确比较；
4. 对完全匹配的 Profile 执行启动和健康检查；
5. 在需求、设备或服务状态不匹配时拒绝复用并重新规划；
6. 测量候选并保存新的配置与报告。
7. 通过 `reconcile` 接收聚合运行指标和当前目标；
8. 使用连续异常窗口和冷却时间过滤瞬时波动；
9. 输出 `KEEP / REBENCH / RECONFIGURE / SWITCH`，并保存不可自动执行的安全计划；
10. 在计划中声明排空、重新验收、Canary 和旧 Profile 回滚要求。
11. 在 LocalPilot API 代理层聚合请求 P95 延迟、错误率和活跃请求数；
12. 通过 `watch` 周期读取实时聚合指标，在出现可执行计划时停止轮询。
13. 通过 `drain` 拒绝新请求并等待在途任务完成，超时自动恢复接流；
14. 通过 `resume` 在变更完成或取消后重新开放业务流量。
15. 通过 `stage` 测量并保存候选，同时保持当前 Profile 不变；
16. 通过 `activate` 在排空状态中预热候选、检查健康并运行业务探针；
17. 激活失败时恢复旧 Profile，并通过同一安全路径支持显式 `rollback`。

当前还没有实现：

- 后台持续监控业务流量和系统资源；
- 不经过 LocalPilot API 代理时的引擎和系统指标自动采集；
- 根据 `reconcile` 计划自动生成并暂存候选；
- 多实例 Canary、原子路由切换和无人值守自动回滚；
- 线上请求排空、Canary、会话迁移和自动回滚；
- 在 DGX Spark 上常驻小型控制 LLM；
- 对赛事方远程 DGX Spark 的完整现场验证。

因此当前准确表述是：

> **LocalPilot 已能根据显式需求和外部提供的聚合指标判断需求、环境及运行漂移，并生成受控调整计划；持续采集和安全在线执行属于下一阶段。**

## 3. 需要发现的变化

### 3.1 显式需求变化

由用户、应用或上游 Agent 提交，包括：

- 任务从聊天变成代码、视觉或 Agent；
- 优先方向从质量变成延迟或吞吐；
- 并发量和上下文长度改变；
- 新增工具调用、推理、结构化输出或多模态要求；
- 隐私边界、语言或质量门槛改变；
- 执行目标从本机切换到远程节点。

这类变化在下一次 LocalPilot 调用时立即处理。

### 3.2 隐性运行变化

用户可能没有修改需求，但原配置已经不能继续满足目标：

| 类型 | 观测信号 | 可能动作 |
|---|---|---|
| 负载漂移 | 并发、队列长度、请求大小持续变化 | 调整队列、batch、并发或模型 |
| 性能漂移 | TTFT、P95 延迟、吞吐持续越界 | 重新测量并诊断瓶颈 |
| 资源漂移 | 可用内存下降、GPU/CPU 争用、温度或功耗受限 | 降低负载或重新规划 |
| 质量漂移 | 真实任务通过率下降、输出契约失败 | 重跑质量集或更换模型 |
| 环境漂移 | 模型、引擎、驱动、CUDA、容器版本改变 | 使旧验收失效 |
| 服务异常 | 健康检查失败、错误率升高、进程重启 | 恢复、回滚或重新部署 |

隐性变化应由监控器采集，由规则引擎触发。LLM 可以协助解释原因，但不负责读取每个原始指标或单独决定是否切换。

## 4. 介入时机

LocalPilot 不应介入每一个推理请求。推荐五类介入点：

1. **首次部署**：完整规划、真实验收和配置交付；
2. **需求改变**：需求指纹不匹配时重新规划；
3. **持续越界**：SLA 连续多次或持续一段时间未达标；
4. **环境改变**：软硬件指纹改变后使旧结果失效；
5. **定期复检**：按天或按周低频确认配置仍然有效。

触发应带防抖和冷却。例如：

```text
P95 TTFT 连续 5 分钟超过 2 秒
且最近 15 分钟没有执行过调整
且当前没有正在进行的验收任务
→ 触发 reconcile
```

一次瞬时峰值只记录告警，不应立刻切换模型。

## 5. 推荐架构

```text
控制端：任意能运行 Agent、Python 和 SSH 的电脑
├── LocalPilot Skill
├── 规则与策略
├── 可选的小型控制 LLM
└── 调度、报告和审批入口
                    │ SSH / 节点 API
                    ▼
执行端：Apple Silicon / DGX Spark / NVIDIA 设备
├── 轻量 LocalPilot Agent
├── 指标采集器
├── 配置执行器
├── 推理引擎
└── 业务模型
```

默认将小型控制 LLM 放在外部控制端。执行节点只保留轻量 Agent，以减少资源干扰并保证基准测试可信。

当设备需要完全离线自治时，可以启用可选的 `Autonomous Node` 模式，将量化小模型部署到 DGX Spark，但应按事件唤醒，而不是持续生成或参与每个请求。

## 6. 小型控制 LLM 的职责与边界

适合由小型 LLM 完成的工作：

- 将自然语言需求转换为结构化验收条件；
- 汇总多个告警和日志，提出可能原因；
- 生成少量候选调整方案；
- 解释为什么保持、重测、调整或换模型；
- 为人类生成可审查的变更说明。

不应只由小型 LLM 完成的工作：

- 判断真实内存是否足够；
- 判断 SLA 是否越界；
- 直接停止已有任务；
- 在没有测试的情况下切换模型；
- 覆盖安全门槛或自动删除回滚点；
- 将推断值写成实测结果。

最终判断必须来自结构化指标、资源检查、真实基准和明确策略。

## 7. DGX Spark 上的资源配比

DGX Spark 使用 CPU 和集成 GPU 共享的 128 GB 一致性统一内存。它不是传统的“系统内存加独立显存”，也没有适合本方案直接假设的固定内存切片。因此控制模型、业务模型、KV Cache、CPU 任务和系统进程会竞争同一个资源池及内存带宽。

推荐资源优先级：

```text
业务请求 > 健康检查与指标采集 > 恢复操作 > 候选验收 > 控制 LLM 分析
```

默认策略：

- 业务模型拥有最高优先级；
- 轻量 Agent 和采集器可以常驻；
- 控制 LLM 按事件启动，并限制上下文和输出长度；
- 资源不足时只给出建议，不自动加载第二个模型；
- 调优测试优先安排在低负载窗口；
- 基准测试时暂停控制模型，或将其开销明确纳入生产基线；
- 不预设固定百分比，先基于实际模型、KV Cache 和系统余量计算预算。

如果使用 MIG 或其他隔离机制，必须先在赛事方具体设备、驱动和系统版本上验证，不能将其作为默认可用能力宣传。

## 8. 调整对已有任务的影响

不同调整的风险不同：

| 调整 | 默认处理 | 风险级别 |
|---|---|---:|
| 限流、队列和新请求并发上限 | 在线调整 | 低 |
| batch 策略 | 小流量验证后调整 | 中 |
| 新请求上下文上限 | 只影响新请求 | 中 |
| KV Cache 配置 | 排空后调整 | 高 |
| 量化版本 | 排空、预热、验收 | 高 |
| 模型或引擎切换 | 受控切换并保留回滚点 | 很高 |
| 新旧大模型同时加载 | 仅在资源检查通过时允许 | 很高 |

需要保护的任务类型：

- 无状态请求：当前请求完成后切换；
- 多轮对话：保存消息历史，新模型重新建立 KV Cache；
- 长文本生成：等待生成完成或到达明确安全点；
- Agent 工作流：在工具调用边界保存检查点；
- 实时语音或视频：先建立新实例，再迁移会话。

## 9. 安全调整状态机

```text
OBSERVING
    ↓ 持续越界或指纹变化
CHANGE_DETECTED
    ↓ 生成候选和影响分析
PLAN_READY
    ↓ 资源足够或进入低负载窗口
WAITING_FOR_SAFE_WINDOW
    ↓ 停止接收会受影响的新任务
DRAINING
    ↓ 已有任务完成
VALIDATING
    ↓ 新配置通过门槛
SWITCHING
    ↓ 业务探针通过
READY

任一阶段失败 → ROLLBACK → READY（旧配置）
```

任何高风险调整必须满足：

1. 旧配置和回滚命令仍然存在；
2. 新配置完成资源预检；
3. 正在执行的任务已完成或已保存检查点；
4. 新配置经过预热和业务探针；
5. 切换后持续观察一段时间；
6. 超时、错误率或性能恶化时自动回滚；
7. 全过程记录触发原因、前后指标和执行结果。

## 10. 控制动作

变化检测后输出四种基础决策：

| 决策 | 含义 |
|---|---|
| `KEEP` | 当前配置仍满足需求，不执行调整 |
| `REBENCH` | 环境或性能发生变化，重新测量原配置 |
| `RECONFIGURE` | 模型仍适合，调整并发、上下文、KV 或引擎参数 |
| `SWITCH` | 当前模型无法满足目标，验收其他模型或引擎 |

CLI 路线：

```bash
localpilot watch --target ssh://pilot@dgx-spark       # 已实现 API 指标轮询
localpilot reconcile --target ssh://pilot@dgx-spark  # 已实现计划生成
localpilot drain --target ssh://pilot@dgx-spark      # 已实现安全排空
localpilot resume --target ssh://pilot@dgx-spark     # 已实现恢复接流
localpilot stage "<goal>" --target ssh://pilot@dgx-spark
localpilot activate <profile-key> --target ssh://pilot@dgx-spark
localpilot rollback <old-profile-key> --target ssh://pilot@dgx-spark
localpilot rollback <deployment-id>
```

其中 `watch` 和 `reconcile` 可以自动运行；高风险 `apply` 只有在安全窗口、自动化策略或明确授权存在时执行。

3. ~~实现性能指标的连续越界判断、冷却时间和变更原因；~~ 已实现；
4. ~~支持拒绝新请求并等待当前任务完成；~~ 已实现；
5. ~~保存旧 Profile，并提供失败恢复与显式回滚路径；~~ 已实现，仍需真实节点演示；
6. 在真实 DGX Spark 上验证一次隐性负载变化；
7. 报告调整前后的 TTFT、吞吐、质量、错误率和资源占用。

### P1：受控在线切换

1. 请求排空；
2. 新配置预热；
3. 小比例 Canary；
4. 业务探针；
5. 自动回滚；
6. 会话和 Agent 检查点处理。

### P2：离线自治

1. DGX Spark 上的按需小型控制 LLM；
2. 多节点调度；
3. 温度、功耗和长期质量漂移；
4. 更严格的资源隔离；
5. 跨设备历史数据驱动的配置推荐。

## 12. 推荐演示脚本

1. 在 DGX Spark 上部署一个满足单用户质量要求的模型；
2. LocalPilot 保存验收 Profile 并进入 `OBSERVING`；
3. 模拟并发持续升高，使 P95 TTFT 连续超过门槛；
4. 规则引擎输出 `CHANGE_DETECTED`，小模型解释变化原因；
5. LocalPilot 提出降低上下文、调整 batch 或切换模型的候选；
6. 系统等待安全窗口，保护当前长任务；
7. 对新配置进行真实验收；
8. 新配置达标后切换，并展示前后指标；
9. 再模拟一次失败，让系统回滚到旧 Profile。

这个演示同时回答四个关键问题：

- 系统如何发现用户没有显式说明的变化；
- LocalPilot 为什么在这个时刻介入；
- 调整为什么不会直接破坏已有任务；
- 小型控制 LLM 提供了什么价值，又受什么规则约束。

## 13. 产品原则

1. 监控和阈值判断优先使用确定性程序；
2. 小型 LLM 负责理解和解释，不单独控制生产资源；
3. 瞬时波动不触发高风险调整；
4. 先验收再切换；
5. 保护已有任务优先于立即优化；
6. 资源不足时降级为建议；
7. 每次高风险改变都必须可回滚；
8. 控制面消耗必须进入资源预算和测量报告；
9. 不把估算、模拟或推断写成真实设备测量；
10. Skill 保持为决策方法，持续运行能力由 Core、CLI 和节点 Agent 实现。
