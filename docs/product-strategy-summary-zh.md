# LocalPilot 产品定位、参赛判断与能力路线总结

> 更新日期：2026-09-21
> 文档性质：产品与研发决策记录
> 证据口径：明确区分“已经实现”“部分实现”“规划能力”，不把模拟结果、设计目标或单候选测量写成已验证效果。

## 1. 结论

LocalPilot 当前最合适的定位是：

> **面向 Apple Silicon、DGX Spark 和本地 NVIDIA 设备的任务驱动推理验收与配置交付系统。控制端可以是任何能运行 Agent、Python 和 SSH 的电脑；执行端可以是本机或远程节点。系统把业务需求转换成验收标准，在真实设备上选择、测量并交付模型配置。**

它不应只被描述成“快速部署模型”或“自动调几个推理参数”。更有价值的能力是：

1. 理解用户要完成的任务和限制；
2. 把自然语言需求转换成可测量的验收门槛；
3. 判断当前瓶颈属于质量、延迟、吞吐、内存还是稳定性；
4. 决定应该换模型、换引擎还是调整运行参数；
5. 在真实设备和真实任务上验收；
6. 交付可调用、可复现、可回滚的配置；
7. 在需求或环境变化后重新判断和调整。

当前项目已经具备需求解析、硬件检测、候选规划、测量、排名和配置记忆的基础，但还没有完整证明“多候选优化后交付一个持续可用服务”的闭环。冲击 130 支参赛队伍中的前十，应优先补齐真实业务效果和交付证据，而不是继续扩大功能范围。

## 2. Skill 最重要的作用

Skill 不是给模型增加新权重，也不是让任意聊天模型读取一个文件后就自动获得真实设备操作能力。

Skill 的核心作用是：

> **把一套专业工作方法、工具调用规则、判断标准和停止条件，交给具有工具调用能力的 Agent 执行。**

在 LocalPilot 中，各部分的职责如下：

| 部分 | 职责 |
|---|---|
| 基础模型 | 理解需求、推理和解释结果 |
| Agent 运行环境 | 读取 Skill、调用命令、接收执行结果 |
| `SKILL.md` | 定义触发条件、工作流程、证据规则和安全边界 |
| LocalPilot Core | 检测、规划、执行、测量、排名、保存和回滚 |
| 推理引擎 | 运行实际业务模型 |
| Apple Silicon / DGX Spark / NVIDIA 设备 | 作为本机或远程真实执行环境 |

因此，更准确的说法是：

> **LocalPilot Skill 让兼容 Agent 按照同一套专业流程，在本机或 SSH 节点上完成推理环境的需求分析、配置选择、真实验收和配置交付。**

普通聊天模型如果不能调用 CLI、API 或设备工具，只能理解这套方法，不能完成真实部署和测量。被部署的视觉、代码或语音模型本身也不需要读取 Skill；读取 Skill 的是上层控制 Agent。

## 3. 当前已经具备的能力

### 3.1 需求解析

当前系统可以从自然语言中提取或推断：

- 任务类型；
- 隐私要求；
- 优先方向；
- 上下文长度；
- 并发量；
- 输入模态；
- 所需能力。

### 3.2 硬件与运行环境检查

当前流程能够检查：

- NVIDIA 硬件和平台类型；
- 可用内存及统一内存特征；
- 内存带宽；
- CUDA、驱动和部分推理引擎状态；
- 模型是否能进入规划内存预算。

### 3.3 候选规划与方向策略

当前策略包含：

- `latency`：首字延迟和单流速度优先；
- `quality`：输出质量优先；
- `throughput`：并发吞吐优先；
- `low_memory`：内存占用优先；
- `long_context`：长上下文和 KV 成本优先；
- `balanced`：多指标折中。

候选参数覆盖模型、引擎、精度、上下文长度、并发宽度、KV Cache 类型、显存利用率、前缀缓存和推测解码等部分配置。

### 3.4 测量、质量判断与配置记忆

当前系统能够：

- 启动或连接候选服务；
- 检查服务健康；
- 测量 TTFT、单流吞吐、聚合吞吐和峰值内存；
- 使用关键词和可选 Judge 信号评价输出；
- 对带标准字段的文档测试集，直接核对 JSON 字段、值和类型，分别报告字段准确率与整张文档通过率；
- 根据显式策略排名；
- 保存硬件相关 Profile；
- 在后续请求中尝试复用 Profile；
- 导出 Markdown 和 JSON 报告。

### 3.5 已验证的真实设备证据

2026-09-20 的报告已经在 DGX Spark GB10 上连接真实 vLLM 服务，测量 Step3-VL-10B-FP8：

- 119.7 GB 可见统一内存；
- TTFT 约 55 ms；
- 单流解码约 20.1 tok/s；
- 引擎报告的权重与已分配 KV 内存约 55.0 GB；
- 系统识别出附着服务实际只运行一个模型和一组配置，删除了标签与真实服务不一致的候选。

最后一项体现了项目的重要原则：**不使用 Agent 推理代替可以获得的真实测量，也不把同一服务伪装成多个不同配置进行比较。**

2026-09-21 又完成了真实图片输入验收。LocalPilot 通过 DGX Spark 上已有的
vLLM 服务向 Step3-VL-10B-FP8 发送一张内嵌合成测试图，连续完成 3 次图片请求。
模型正确识别了左侧红色、右侧蓝色和中心绿色，三个预期字段必须全部命中才算通过。
本次实测 TTFT 为 98.76 ms，单流解码为 20.19 tok/s，报告记录的峰值内存为
55.04 GB，来源是引擎报告的权重与已分配 KV 内存。

随后在同一服务上完成了 6 张合成英文票据的字段验收：30/30 个字段精确匹配，
6/6 张文档全部通过，JSON 有效率 100%，请求失败 0。3 次独立性能请求的平均
首字延迟约 0.95 秒，完整响应平均约 12.35 秒。此结果只适用于该小型合成数据集，
且尚未达到此前设想的完整响应低于 2 秒目标。

## 4. 当前不能过度声称的能力

### 4.1 已证明合成票据字段验收，尚未证明真实文档业务效果

最新报告已经证明图片被实际组装进 OpenAI 兼容请求，并在 DGX Spark 上完成
3 次非模拟测量。合成测试图的红、蓝、绿三个确定性字段全部命中，说明从
LocalPilot 基准集、请求构造到视觉模型响应的图片链路已经跑通。

新的合成票据验收进一步证明了 6 张干净英文图片上的字段提取，包含票据编号、
日期、金额、卖方及可缺省的采购单号。验收使用严格 JSON 字段比较，字段准确率
与整张文档通过率分别记录，失败请求仍进入分母；没有调用独立语义 Judge。

这仍不能证明：

- 中文税务发票、扫描件、倾斜或低清文档的 OCR 可用；
- 真实业务数据分布上的字段准确率达到目标；
- `local_only` 已由网络策略强制执行，而不只是本次使用回环端点；
- 多个视觉候选之间完成了有效比较；
- 没有独立 Judge 时，开放式视觉回答具备可靠质量。

### 4.2 还没有证明多候选优化

最新真实报告只有一个可测候选。单候选能够证明测量链路，但不能证明系统从多个模型、引擎或配置中选出了更优方案。

单候选产生的“winner”和归一化分数只能表示流程结果，不能回答“比默认方案提升了多少”。

后续已补充一次**请求输出策略**的有效单因素对照：同一设备和模型，6 张合成
票据各重复两轮，只改变 `response_format`，完整响应平均从 9.764 秒降到
3.138 秒，两组字段均为 60/60 正确。标准流程独立复验也通过。
这已经证明该场景下的一项输出策略优化收益，但尚未证明跨模型选择、
引擎参数调优或 GPU 每 token 推理加速。见
[配对实验与复用配置](../results/20260921-output-strategy-comparison.md)。

### 4.3 “READY”还不等于持续部署

候选完成测量后，执行器会停止 LocalPilot 管理的模型。系统随后保存 Profile 并标记 `READY`，API 请求到来时再尝试恢复服务。

因此当前更准确的状态是：

- 已测量；
- 已选择；
- 已保存配置。

尚未完整证明：

- 获胜模型持续运行；
- API 端点立即可用；
- 进程退出或重启后自动恢复；
- 失败时自动回滚到上一个可用配置。

### 4.4 显式需求变化已经纳入 Profile，持续漂移检测尚未实现

当前 Profile 匹配已经纳入硬件指纹、任务、优先方向、模拟状态、隐私、质量等级、上下文长度、并发量、输入模态、能力要求、语言和基准配置哈希。上述结构化条件或验收集内容发生变化时，旧 Profile 不会直接复用；完全匹配时也会先执行启动与健康检查。

仍未完整纳入或实现的部分包括：

- 具体质量、延迟和吞吐 SLA；
- 独立 Judge 的模型与评分规则版本；
- 模型 revision、引擎、驱动和容器版本的完整环境指纹；
- 业务流量、性能、资源和质量漂移的后台持续检测；
- 变化后的在线排空、Canary、切换和自动回滚。

详细方案见 [`adaptive-control-design-zh.md`](adaptive-control-design-zh.md)。

### 4.5 隐私目前主要是声明，不是强制策略

用户可以要求 `local_only`，但系统仍需要进一步验证候选端点、Judge 端点和日志链路是否真的位于允许的网络边界内。

### 4.6 安装与复现存在提交风险

这两个问题已在 2026-09-20 的后续改造中修复：`models/` 忽略规则已限定为仓库根目录，运行配置也已经作为 package data 进入 wheel。当前工作树已完成仓库外临时虚拟环境安装和完整 mock autopilot 验收；提交后仍需再做一次基于提交版本的干净克隆验收。

## 5. 对前十竞争力的判断

根据公开参赛材料中记录的评分维度进行非官方粗评：

| 维度 | 当前粗评 | 判断 |
|---|---:|---|
| 实用价值与技术创新 | 17/25 | 定位有价值，用户收益尚未量化 |
| Agent 与模型优化深度 | 14/25 | 有职责分层，真实调优比较不足 |
| 完整度 | 9/20 | 干净安装和持续交付链路存在缺口 |
| DGX Spark 适配 | 11/15 | 已有真实设备测量，但验证面较窄 |
| 演示效果 | 4/10 | 当前目标与实际输入不一致 |
| 文章与研发记录 | 3/5 | 技术诚实性好，核心故事需继续收敛 |
| **合计** | **约 58/100** | 有技术基础，但当前版本不应视为稳进前十 |

这个分数不是官方结果，也不是对最终名次的预测。它用于暴露当前最可能失分的环节。

项目进入前十的主要机会是：

1. DGX Spark 上的真实运行证据；
2. “拒绝虚假比较”的可信工程方法；
3. 从任务需求出发，而不是从模型排行榜出发；
4. 需求变化后自动重新验收和切换配置；
5. 把验收结果交付为实际可调用服务。

## 6. 应当收缩或暂时退出主演示的能力

以下能力可以保留为规划或实验代码，但不应在当前主演示中作为已完成能力宣传。

### 6.1 音频

当前测试只有文字形式的“转写并回答”，没有真实音频输入和 ASR 指标。

### 6.2 Embedding

当前测试没有调用 embeddings endpoint，也没有召回率、排序质量或 RAG 效果评测。

### 6.3 Agentic Tool Use

当前主要测试模型能否描述工具调用步骤，没有真正执行工具调用并验证任务结果。

### 6.4 全引擎自动优化

vLLM 路径最接近真实可用。NIM、TensorRT-LLM、SGLang 和 llama.cpp 应在各自具备真实启动、测量和失败恢复证据后再进入核心宣传。

### 6.5 “多个 Agent”作为主要创新

Planner、Bench、Judge 的职责划分是合理架构，但 Agent 数量本身不是价值。应展示每个 Agent 做出了什么可验证决策、调用了什么工具、如何处理失败。

## 7. 推荐的主演示场景

建议将比赛主演示固定为：

> **在 DGX Spark 上，根据隐私、准确率、延迟和并发要求，自动选择并交付本地视觉文档模型；需求变化后重新验收并切换配置。**

推荐使用 10～20 张脱敏或合成发票，至少评测：

- 发票号码 exact match；
- 日期 exact match；
- 金额数值误差；
- 商户名称；
- 字段完整率；
- TTFT；
- P50/P95 响应延迟；
- 并发吞吐；
- 峰值内存；
- 失败率和重启恢复。

质量验收应以确定性的字段比对为主，Judge 模型只能作为辅助信号。

### 两分钟演示建议

1. 用户输入：“发票不能离开本机，字段准确率至少 95%，响应低于 2 秒。”
2. LocalPilot 检查 DGX Spark 并生成验收规则。
3. 系统顺序启动两个真实视觉候选。
4. 使用真实图片测试字段准确率、延迟和内存。
5. 一个候选速度更快但准确率不足，被质量门槛淘汰。
6. 系统部署满足门槛的获胜配置。
7. 现场调用 API，返回结构化发票 JSON。
8. 把需求改为“8 个用户并发”，旧 Profile 被判定不适用。
9. 系统重新验收、切换配置，并保留旧配置作为回滚点。

## 8. 方向调优应成为核心能力

方向调优与模型训练或微调不是同一件事。

- **方向调优**：判断应该优化质量、延迟、吞吐、内存、上下文还是稳定性；
- **推理调优**：选择模型、引擎、量化、KV Cache、batch、并发、前缀缓存和推测解码；
- **模型微调**：LoRA、SFT 等改变模型权重，当前不属于 LocalPilot 的直接执行范围。

推荐的闭环是：

```text
业务需求
  → 生成验收门槛
  → 测量当前配置
  → 找出未达标指标
  → 诊断瓶颈
  → 选择调整方向
  → 生成最小候选集合
  → 重新验收
  → 部署、记录和回滚
```

不同失败应触发不同动作：

| 未达标指标 | 优先调整方向 |
|---|---|
| 任务准确率 | 提示词/结构化输出、模型、精度、领域模型；仍失败时建议 LoRA/SFT |
| 首字延迟 | 模型大小或稀疏性、精度、引擎、推测解码、预热 |
| 并发吞吐 | batch、`max_num_seqs`、队列、前缀缓存、引擎 |
| 内存占用 | 权重量化、KV 精度、上下文、并发、模型大小 |
| 长上下文 | KV 成本、上下文策略、模型架构、检索或分段 |
| 稳定性 | 保守配置、失败恢复、上一个稳定 Profile |

方向调优的输出应当包含：

- 哪个业务门槛没有达到；
- 实际测量值；
- 瓶颈类型；
- 为什么选择下一步动作；
- 哪些变量保持不变；
- 哪些变量需要改变；
- 新配置是否通过重新验收。

## 9. 需求变化后的自适应机制

需求变化是非常适合加入的能力，也是 LocalPilot 相对普通部署工具的重要差异。

建议为每次需求生成 `requirement_fingerprint`，至少包含：

- task 和 modality；
- 输入输出契约；
- context length；
- concurrency；
- privacy；
- quality/latency/throughput/memory SLA；
- capability requirements；
- evaluation pack 及其版本；
- 模型与引擎允许范围。

同时记录 `environment_fingerprint`：

- 设备和可用内存；
- 驱动和 CUDA；
- 模型 revision；
- 引擎版本；
- 容器 image digest；
- 启动参数。

只有需求和环境仍兼容，Profile 才能直接复用。否则系统应进行增量重测或完整重验收。

## 10. 远程部署与配置

远程能力适合加入，但要区分两种模式。

### 10.1 推荐模式：Agent 在目标设备执行

通过 SSH、远程 Agent 或节点服务在目标 DGX Spark 上运行 LocalPilot。硬件检测、模型启动和测量都发生在目标设备，控制端只接收结构化结果。

### 10.2 有限模式：控制端只连接远程推理 API

这种模式可以测量端到端 API 延迟和输出质量，但控制端不能可靠声明：

- 目标设备的真实峰值内存；
- GPU 利用率；
- 实际启动参数；
- 模型文件和数据是否完全本地；
- 服务是否由 LocalPilot 管理。

因此，远程部署需要目标节点 Agent、身份认证、权限边界、日志脱敏、传输加密和回滚机制，不能只把 `BASE_URL` 指向远程地址就称为远程设备管理。

## 11. 端侧大模型时代的长期价值

端侧设备能运行越来越大的模型后，问题会从“能不能运行”转变为：

> **应该运行哪个模型和配置，是否满足当前任务，以及设备和需求变化后如何持续满足目标。**

未来需要处理的动态条件包括：

- 可用内存变化；
- 温度和功耗限制；
- 电池电量；
- GPU/NPU/CPU 资源抢占；
- 网络连接和云端可用性；
- 模型或操作系统更新；
- 摄像头、麦克风和传感器模态；
- 用户任务和隐私边界变化。

基础部署功能会逐渐被设备和操作系统厂商标准化。LocalPilot 的长期壁垒不应是某个启动命令，而应是：

1. 业务需求到验收标准的转换；
2. 跨模型、跨引擎、跨设备的统一测量；
3. 对性能和质量瓶颈的正确诊断；
4. 需求变化后的自动重新选择；
5. 真实设备上的历史 Profile 和比较数据；
6. 可解释、可复现、可回滚的配置交付。

长期定位可以扩展为：

> **面向端侧 AI 设备的任务驱动模型运行控制层：根据业务目标、设备资源和运行状态，自动选择、验收、部署并持续调整本地模型。**

## 13. 对外表达建议

### 一句话版本

> LocalPilot 让通用 Agent 获得跨本机与远程节点的本地推理验收与配置交付能力。

### 产品版本

> LocalPilot 把业务需求转换成可测量的验收门槛，在 Apple Silicon、DGX Spark 等本机或远程设备上选择、测量并交付模型配置，并在需求或运行环境变化后重新验收和调整。

### 路演版本

> 过去部署本地模型靠工程师反复试模型和参数。LocalPilot 让 Agent 读取业务目标，在真实设备上比较候选，淘汰不满足质量或性能门槛的配置，交付一个可调用端点，并在需求变化后自动重新选择。

### 不建议使用的表述

- “任何模型读取一个文件就自动获得全部能力”；
- “已经支持所有模态和所有推理引擎”；
- “一次运行就找到了全局最优参数”；
- “单候选测量证明 LocalPilot 优化了性能”；
- “写了 local-only 就证明数据从未离开设备”；
- “READY 一定代表推理服务正在持续运行”。

## 14. 最终产品原则

1. **真实任务优先于通用样例。**
2. **业务门槛优先于相对分数。**
3. **测量优先于模型推断。**
4. **交付可用端点优先于生成配置建议。**
5. **需求变化必须触发配置有效性判断。**
6. **模拟、真实测量、设备部署和生产验证必须分开表述。**
7. **少量完整能力优先于大量未验证能力。**
8. **每个结论都应能追溯到设备、配置、测试集和运行记录。**
